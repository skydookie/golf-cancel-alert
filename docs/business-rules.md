# business-rules.md — 도메인 로직

## App User

- 이메일 + 비밀번호로 가입한다. **유효한 초대코드 없이는 계정이 생성되지 않는다** — 초대코드가
  틀리거나 없으면 가입 요청 자체가 거부되고, 이메일 중복 검사조차 실행되지 않는다.
- 같은 이메일로 두 번째 가입을 시도하면 거부된다(이메일이 사용자 식별자).
- 자기 자신이 등록한 FacilityCredential, WatchCondition, SlotObservationState, NotificationLog,
  PushSubscription에만 접근할 수 있다. 다른 User의 리소스에 접근을 시도하면(존재하지 않는 것과
  동일하게) 404로 응답한다 — 리소스가 "다른 사람 것이라 못 봄"인지 "아예 없음"인지 구분해서 알려주지
  않는다(존재 자체를 숨김).
- 계정을 탈퇴하면 위 다섯 종류의 자기 데이터가 전부 즉시, 완전히 삭제된다(소프트 삭제/보관 없음).
  탈퇴 후에는 같은 이메일로 다시 가입할 수 있다.

## Facility (골프장 사이트)

- 하나의 Facility = 하나의 사이트-어댑터 구현체. 현재 등록된 Facility는 `laviebelle-old`
  (라비에벨 올드코스) 하나뿐이다. `laviebelle-new`(뉴코스)는 실사이트 구조가 올드코스와
  동일한지 실사이트로 확인되지 않아 아직 등록하지 않았다.
- 같은 Facility라도 **로그인한 회원의 등급/타입에 따라 보이는 잔여 시간표와 요금이 달라질 수
  있다**(실사용자 확인 사실). 그래서 한 Facility를 감시하는 로직이라도 User마다 독립적으로
  로그인·스캔한다 — 어느 한 User의 스캔 결과를 다른 User에게 재사용하지 않는다.

## Facility Credential (골프장 계정)

- (User, Facility) 조합마다 최대 1개. 같은 조합을 다시 등록하려는 요청은 거부된다(대신
  갱신 API를 쓰게 한다).
- 상태는 `ACTIVE`(정상 감시 중) 또는 `PAUSED_LOGIN_FAILED`(로그인 실패로 감시 중지) 둘 중
  하나다. 세 번째 상태 없음.
- `ACTIVE` → `PAUSED_LOGIN_FAILED` 전환: 감시 사이클이 이 자격증명으로 로그인을 시도했는데
  실패했을 때(아이디/비밀번호 불일치, 계정 잠김 등 — "자격증명 자체의 문제"로 판별된 경우만).
  네트워크 오류나 사이트 일시 장애로는 이 상태로 전환되지 않는다(재시도 대상으로 남는다).
- `PAUSED_LOGIN_FAILED` → `ACTIVE` 전환: 그 자격증명의 아이디 또는 비밀번호가 갱신될 때
  **자동으로**(사람이 별도로 "재개" 조작을 할 필요 없음). 갱신되지 않으면 자동으로 재개되지
  않는다 — 감시 사이클은 `PAUSED_LOGIN_FAILED` 상태인 자격증명에 대해 로그인을 재시도하지 않는다
  (무한 재시도로 실제 회원 계정이 잠기는 사고를 막기 위함).
- 로그인 아이디/비밀번호는 둘 다 가역 암호화로 저장된다(감시 사이클이 실제로 그 값을 써서
  로그인해야 하므로). 이는 App User 자신의 로그인 비밀번호(단방향 해시)와 저장 방식이 다르다 —
  둘을 혼동하면 안 된다.

## Watch Condition (관심조건)

- User가 만드는 조건 = 날짜 목록(구체적인 날짜를 하나 이상 콕 찍음, 기간/요일 패턴 아님) +
  시간대 범위(시작 HH:mm ~ 종료 HH:mm, 시작 < 종료).
- 코스(OUT/IN) 구분과 인원수 조건은 없다 — 날짜가 목록에 있고 시간이 범위 안(경계값 포함)이면
  코스에 상관없이 매칭 대상이다.
- User당 개수 제한 없음.
- 삭제 전까지 계속 유지된다. 알림을 한 번(또는 여러 번) 보냈다고 자동으로 삭제되거나 비활성화되지
  않는다 — 계속 같은 조건으로 감시한다.

## Available Slot / 전환 판정 (감시 사이클의 핵심 규칙)

- 슬롯의 식별 키 = (Facility, 날짜, 코스, 시간). 요금은 식별에 포함되지 않는다 — 같은 키에서
  요금만 바뀌어도 같은 슬롯으로 취급하고, 재알림하지 않는다.
- 사이트가 돌려주는 날짜별 시간표 목록에는 **지금 신청 가능한 시간대만** 나타난다. 이미 예약이
  끝난 시간대는 그 목록에 아예 나타나지 않는다(회색 표시 등으로 남지 않는다 — 실사용자가 실제
  화면으로 확인한 사실). 그래서 "이전엔 목록에 있었는데 이번엔 없다"는 곧 "신청 불가로 바뀌었다"는
  뜻으로 해석한다.
- 예약 캘린더 화면에는 "예약(신청 가능)", "마감", "오픈전" 세 가지가 시각적으로 구분되어 표시되지만,
  감시 로직은 "마감"과 "오픈전"을 구분하지 않는다 — 둘 다 "신청 불가" 상태로 동일하게 취급한다.
  정상적으로 처음 열리는 날짜(오픈전 → 예약)와 취소로 다시 열리는 날짜(마감 → 예약)를 같은
  "신청 불가 → 신청 가능" 전환으로 처리한다(사용자에게는 어느 쪽이든 "지금 신청할 수 있게 됐다"는
  사실이 동일하게 중요하기 때문).
- 알림 발생 규칙: 어떤 슬롯이 "신청 불가 → 신청 가능"으로 전환됐고, 그 시점에 어떤 User의
  활성 관심조건(날짜+시간대 범위)과 일치하면, 그 User에게 알림 1건을 보낸다.
  - 이미 신청 가능 상태가 유지 중인 슬롯은 재알림하지 않는다(매 스캔마다 같은 상태면 조용히
    상태만 유지).
  - "신청 가능 → 신청 불가 → 다시 신청 가능"으로 재전환되면, 재전환 시점에 **새 알림**을 보낸다
    (이전에 알림을 받았었다는 사실이 재알림을 막지 않는다 — 오직 "현재 신청 불가 상태였는가"만
    본다).
  - 같은 스캔 주기에 조건에 맞는 슬롯이 여러 개 동시에 새로 열리면, 하나로 묶지 않고 슬롯마다
    개별 알림을 보낸다.
- 슬롯 상태는 (User, Facility, 날짜, 코스, 시간)별로 독립적으로 추적한다. 회원 등급 차이로 한
  User에게는 보이는 슬롯이 다른 User에게는 안 보일 수 있으므로, 한 User의 관측 결과를 다른
  User의 판정에 쓰지 않는다.

## Notification

- 발송 조건과 개별 발송 규칙은 위 "전환 판정" 항목과 동일하다(알림은 전환 판정의 결과일 뿐, 별도
  규칙을 갖지 않는다).
- 전달 방식은 웹 푸시 하나뿐이다(문자/카카오톡 등 다른 채널 없음).
- 알림에는 최소한 날짜·코스·시간·요금과, 그 날짜로 연결되는 딥링크가 포함된다.
- 알림 이력(NotificationLog)은 영구 보관되며 별도 삭제 기능이 없다(단, User 탈퇴 시 그 User의
  이력은 연쇄 삭제된다).

## 골프장 로그인 실패 알림

- 어떤 자격증명이 로그인 실패로 `PAUSED_LOGIN_FAILED`가 되면, 그 즉시 해당 User에게 웹 푸시로
  알린다(취소표 알림과는 다른 메시지 — "계정 정보를 확인해주세요"). 이 알림은 관심조건 매칭
  여부와 무관하게 항상 간다.

## 딥링크

- User가 스케쥴 화면에서 슬롯을 클릭하면 그 Facility 어댑터가 만든 딥링크 URL로 새 창이 열린다.
- 앱은 이 딥링크를 열 때 로그인을 대신 해주지 않는다 — User가 자신의 브라우저에서 직접
  로그인하고 예약을 완료해야 한다. 감시 사이클이 쓰는 자동 로그인 세션과는 완전히 분리되어 있다.
