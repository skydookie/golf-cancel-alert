# findings.md — 미해결 문제

## 라비에벨 사이트의 실제 HTML 구조가 검증되지 않음

**증상**: `src/lib/adapters/laviebelle.ts`의 캘린더/시간표 파서(`parseCalendarHtml`,
`parseDaySlotsHtml`)와 로그인 경로(`LOGIN_PATH`)·폼 필드명(`id`/`pwd`)은 사용자가 실제
로그인해서 캡처해준 **화면 스크린샷**을 근거로 만든 추정 구조다. 실제 페이지의 HTML
소스(태그/클래스명/폼 구조)는 이 프로젝트 세션 안에서 확보되지 않았다.
**왜 지금 못 고치나**: 골프장 사이트는 로그인이 필요한 회원 전용 화면이라, 실제 계정을 가진
사용자가 브라우저에서 "페이지 소스 보기"로 직접 가져다줘야 확인할 수 있다 — 코드만 읽어서는
해결할 수 없는 외부 의존 정보다.
**영향 범위**: 실사이트 구조가 여기서 가정한 것과 다르면 `scanBookableDates`/`scanDaySlots`가
빈 배열을 반환하거나 잘못된 값을 파싱해, 감시 기능 전체가 조용히 아무 취소표도 못 찾을 수
있다. 로그인 경로/필드명이 다르면 매 사이클 `LoginFailedError`로 계정이 잠길 수 있다.
**접근 방향**: 사용자가 실제 화면의 HTML 소스를 제공하면 `parseCalendarHtml`/
`parseDaySlotsHtml`/`login()`의 선택자·경로·필드명을 그에 맞게 수정하고,
`tests/fixtures/laviebelle-*.html`도 실제 구조를 반영하도록 교체한다.

## 뉴코스(`laviebelle-new`)의 존재 여부와 구조가 확인되지 않음

**증상**: 사용자는 "올드코스+뉴코스 모두 감시"를 원했지만, 뉴코스의 실제 URL 경로나 올드코스와
동일한 로그인 세션을 공유하는지가 이 세션 안에서 확인되지 않았다.
**왜 지금 못 고치나**: 실사이트에 뉴코스 메뉴/URL이 실제로 존재하는지 직접 접속해서 확인해야
하는 정보다.
**영향 범위**: 뉴코스에 대한 취소표는 이번 구현에서 전혀 감시되지 않는다(`src/lib/facilities.ts`
에 `laviebelle-new`가 등록되지 않음).
**접근 방향**: 실사이트에서 뉴코스 경로를 확인한 뒤, 구조가 올드코스와 같으면
`laviebelle.ts`에 설정값만 추가, 다르면 `SiteAdapter`를 구현하는 새 파일을 추가하고
`facilities.ts`/`registry.ts`에 등록한다.

## 취소표 클릭 시 날짜별 화면으로 직접 연결되는 딥링크가 가능한지 확인되지 않음

**증상**: `laviebelleOldCourseAdapter.buildDeepLink`는 현재 항상 예약 캘린더 메인 화면
URL을 반환한다(날짜별 직접 링크를 시도하지 않는 안전한 기본값).
**왜 지금 못 고치나**: 사이트가 날짜별 상태를 URL 쿼리 파라미터로 받는지, 아니면 폼
제출/세션 상태를 거쳐야만 그 화면에 도달하는지가 실사이트 구조 확인 없이는 알 수 없다.
**영향 범위**: 사용자가 "가능하면 해당 날짜 화면으로 바로 연결"을 원했으나, 지금은 항상
캘린더 화면에서 한 번 더 그 날짜를 직접 클릭해야 한다 — 기능 자체는 동작하지만 사용자가
원한 최적 경험(원클릭)에는 못 미친다.
**접근 방향**: 실사이트 구조 확인 후, 날짜별 직접 링크가 가능하면 `buildDeepLink`가 해당
URL을 구성하도록 수정한다.

## 실제 PostgreSQL/실제 VAPID 키를 쓴 종단 간(end-to-end) 검증이 없음

**증상**: 모든 자동화 테스트는 Prisma client를 mock으로 대체해서 실행된다(`npm test`는 실제
DB 없이 통과). 실제 배포 환경(진짜 PostgreSQL, 진짜 VAPID 키, 진짜 브라우저 푸시 수신)에서의
동작은 이 세션 안에서 확인할 방법이 없었다(배포된 인프라 자체가 없음).
**왜 지금 못 고치나**: 실제 클라우드 자원(DB 인스턴스, 배포 URL)이 필요한 검증이라 로컬
세션에서 완결할 수 없다.
**영향 범위**: 스키마 마이그레이션이 실제 PostgreSQL에 문제없이 적용되는지, 웹푸시가 실제
안드로이드/iOS 기기에 도달하는지는 배포 후 최초 확인이 필요하다.
**접근 방향**: 무료 티어 PostgreSQL·Vercel에 최초 배포한 뒤, 회원가입 → 관심조건 등록 →
(테스트용으로 짧게 스캔 주기를 당겨) 알림 수신까지 한 번 수동으로 확인한다.
