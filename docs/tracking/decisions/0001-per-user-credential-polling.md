# 0001 — 대표 계정 공용 감시가 아니라 User별 개별 로그인·스캔

**맥락**: 감시 대상 User가 여러 명(지인 포함)이 되면서, 매번 각 User의 골프장 계정으로
개별 로그인하는 대신 대표 계정 하나로 한 번만 스캔해서 모두에게 결과를 나눠주는 방안을
검토했다 — 로그인 횟수가 줄어 계정 잠김 위험이 낮아지고 구현도 단순해지기 때문이다.

**결정**: 각 User가 등록한 자신의 골프장 계정으로 **개별적으로** 로그인·스캔한다. 대표 계정
공용 방식은 채택하지 않는다.

**대안과 기각 사유**: 대표 계정 1개로 공용 감시하는 방식을 사용자에게 제안했으나, "회원
등급/타입에 따라 보이는 잔여 시간표나 요금이 다를 수 있다"는 답을 받았다 — 즉 한 계정의
스캔 결과가 다른 회원에게는 틀린 정보일 수 있다는 뜻이다. 공용 계정 방식은 이 사실과
양립할 수 없어 기각했다.

**결과**: (User, Facility)마다 별도로 로그인이 필요해, User 수만큼 로그인 빈도가 늘어난다
(계정 잠김 위험 증가 — 로그인 실패 시 그 계정에 대해 반복 재시도하지 않는 규칙으로 부분 완화됨).
FacilityCredential을 User마다 따로 등록·암호화 저장해야 한다(스키마에 `userId` +
`facilityId` 복합 유니크 제약으로 반영됨). 관심조건이 없는 User의 자격증명은 로그인 자체를
건너뛰어 불필요한 로그인 빈도를 줄인다(`scanCycle.ts`).
